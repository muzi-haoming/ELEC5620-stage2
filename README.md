# ELEC5620 Stage 2 · Second Space

A second-hand furniture marketplace: a React frontend and a FastAPI backend, with LangGraph orchestrating 7 Agents (Listing, Pricing, Matching, Logistics, Payment, Audit Reporting and Supervision). Data is stored in Google Cloud SQL for PostgreSQL.

> This project is at the demo stage: external services such as bank payments and delivery carriers are simulated, and users sign in as demo roles.

## Quick start

**Requirements**: Python 3.12, Node.js 22+, and the University of Sydney VPN (needed to call the campus-qwen model).

**First-time setup** (run from the repository root):

Windows (PowerShell):

```powershell
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
npm ci --prefix frontend
Copy-Item .env.example .env
```

macOS (Terminal):

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
npm ci --prefix frontend
cp .env.example .env
```

Edit `.env`: fill in `DATABASE_URL` (database connection) and `MODEL_API_KEY`, and set `DEMO_MODE=true`. `.env` contains secrets; never commit it to Git.

**Start** (two terminals, both in the repository root):

Windows (PowerShell):

```powershell
# Terminal 1: backend, port 8001
.venv/Scripts/python.exe -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8001

# Terminal 2: frontend, port 5622
npm run dev --prefix frontend
```

macOS (Terminal):

```bash
# Terminal 1: backend, port 8001
.venv/bin/python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8001

# Terminal 2: frontend, port 5622
npm run dev --prefix frontend
```

Open http://127.0.0.1:5622/ in a browser. To stop, press `Ctrl + C` in each terminal.

On Windows you can instead double-click `Start-Second-Space.cmd` in the repository root to start both in the background. This opens no terminal windows; logs are written to the `.runtime/` folder, and you stop the app by ending the python and node processes in Task Manager. The `.cmd` launchers are Windows-only; on macOS use the commands above.

API docs: http://127.0.0.1:8001/docs

## Features

**Seller**
- Upload front, top and side photos plus up to 2 detail photos (≤ 15 MB each, HEIC supported).
- The Listing Agent reviews photos and details leniently; if a listing is rejected, it gives a reason and a suggested fix, and the seller can edit and resubmit.
- The Pricing Agent tries, in order: live comparison on public second-hand marketplaces → historical comparison from the last 30 days → AI estimate. If all fail, the seller sets the price.

**Buyer**
- Enter preferences and the Matching Agent recommends up to 3 items.
- Enter delivery details to get a fixed delivery quote, with property confirmation at both ends when needed.
- Simulated payment (Visa / Mastercard or BPAY). Order flow: awaiting pickup → in transit → received → settled immediately after the buyer accepts.

**Manager**
- **Agent Console**: shows what each Agent is doing in real time, plus today's counts, rule blocks and conflicts.
- **Business Data**: daily business report (generated by the Audit Reporting Agent), a trend chart with selectable ranges, and order details.
- **Exceptions & Conflicts**: stall alerts; for an Agent conflict, choose which side to support. Approval creates a new policy version, and later conflicts of the same kind are handled automatically under that policy.
- **Policies**: view active policies and their full version history.

## Architecture

Routine tasks are routed straight to the relevant worker Agent by the Dispatch code node, and the Supervision Agent handles conflicts only. When no policy applies, the workflow pauses and is saved as a PostgresSaver checkpoint until the manager decides. Every result passes business rule checks before commit, and a failed check rolls back the whole action; after commit, the Audit Reporting Agent re-checks it in the background.

## Testing

Tests use only a separate database whose name contains `secondspace_test`. Set `TEST_DATABASE_URL` to it; never point it at the shared demo cloud database.

```powershell
.venv/Scripts/python.exe -m pytest backend/tests -q
npm test --prefix frontend
npm run build --prefix frontend
node frontend/tests/api-flow.mjs
```

On macOS, run the backend tests with `.venv/bin/python -m pytest backend/tests -q`; the other commands are the same.

The browser test (`api-flow.mjs`) creates E2E test listings and orders and approves the sample conflict, so run it in a dedicated test environment.

## Deployment

All container options serve the app at http://127.0.0.1:5623/ (Nginx serves the frontend and proxies `/api` to the backend). Pick **one** option; Compose and kind both use port 5623.

### Configuration

Copy `.env.example` to `.env` and fill in:

| Variable | Meaning |
|---|---|
| `DATABASE_URL` | PostgreSQL URL. For Google Cloud SQL: `postgresql://USER:URL_ENCODED_PASSWORD@PUBLIC_IP:5432/DB?sslmode=require` |
| `MODEL_BASE_URL` / `MODEL_NAME` / `MODEL_API_KEY` | OpenAI-compatible model endpoint (`campus-qwen`, needs the USyd VPN) |
| `MODEL_MODE` | `live` for real model calls, `fixture` for offline tests only |
| `DEMO_MODE` | `true` to enable demo role sign-in |
| `POSTGRES_PASSWORD` | Only for the local PostgreSQL options below (URL-safe) |

For Cloud SQL, allow your machine's public IP in the instance's authorized networks. The backend creates the schema and seed data on first start.

### Option A: Docker Compose + Google Cloud SQL

Requires Docker Desktop (Linux containers).

```bash
docker compose up --build -d      # reads .env; use APP_ENV_FILE=.env.cloud to switch
docker compose ps                 # wait until backend is healthy
curl http://127.0.0.1:5623/api/health
docker compose down               # stop; do not add -v, or uploaded photos are lost
```

On Windows, `Start-Containers.cmd` does the same and copies existing photos from `.runtime/uploads` into the container volume.

### Option B: Docker Compose + local PostgreSQL

No cloud database needed. Set `POSTGRES_PASSWORD` in `.env`, then:

```bash
docker compose -f compose.yaml -f compose.local.yaml up --build -d
```

### Option C: kind (local Kubernetes)

Requires Docker Desktop, [kind](https://kind.sigs.k8s.io/) and kubectl. From PowerShell:

```powershell
./scripts/deploy-kind.ps1 -DatabaseMode CloudSQL            # reads .env.cloud by default
./scripts/deploy-kind.ps1 -DatabaseMode Local -EnvFile .env  # in-cluster PostgreSQL
kubectl --context kind-second-space -n second-space get pods
```

The script creates a `second-space` cluster, builds and loads both images, creates the Secret from the env file over stdin (no secret manifest is written), and waits for the health check. Re-run it after code changes. Deleting the cluster deletes its volumes.

### Moving photos

Photos live on disk, not in the database. After the containers are up, copy existing photos in with `./scripts/copy-uploads.ps1 -Target Compose` (or `-Target Kind`).

More detail (Cloud SQL TLS, model check, verification) is in the [deployment guide](docs/DEPLOYMENT.md) (Chinese).

## Demo notes

- "Reset data" in the business simulation window clears and restores the demo data in the shared cloud database, including teammates' test data.
- Photo files are stored on the computer running the backend (`.runtime/uploads`); the database keeps references only. Copy the photos too when demoing on another computer.
- If a model call fails, that action pauses and asks you to retry; rules never stand in for model output.
- Restart the backend after disconnecting or reconnecting the VPN.
